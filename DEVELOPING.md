# New Relic Video Core

## Build

Install dependencies:

```
$ npm install
```

And build:

```
$ npm run build:dev
```

Or if you need a production build:

```
$ npm run build
```

## Usage

Add **scripts** inside `dist` folder to your page.

> If you want to know how to generate `dist` folder, refer to **npm commands** section.

## Release

- Create a PR.
- Once approved, Update the package version according to the semver rules.
- Update the CHANGELOG in the repo (all web repos have a changelog file).
- Create a github tag with the version.

### Changelog format

`CHANGELOG.md` is generated by `semantic-release` using `.releaserc.json`
(the `conventionalcommits` preset with a custom `presetConfig.types`
mapping). Each entry looks like:

```
## [5.0.1](https://github.com/newrelic/video-core-js/compare/v5.0.0...v5.0.1) (2026-08-05)

### New features

- ...

### Improvements

- ...

### Bug fixes

- ...
```

- The version heading is always `## [x.y.z](compare-url) (YYYY-MM-DD)`.
- Only three sections are surfaced publicly: `New features` (from `feat`
  commits), `Improvements` (from `perf` commits), and `Bug fixes` (from
  `fix` commits). Other commit types (`chore`, `docs`, `style`, `refactor`,
  `test`, `build`, `ci`, `revert`) are hidden from the changelog by
  `presetConfig.types` — they still count for the commit-analyzer's version
  bump decision (`.releaserc.json`'s `commit-analyzer` still runs the
  `angular` preset), they just don't get their own section here.

This exact shape matters beyond readability: `release-publish.yml` extracts
a single version's block from `CHANGELOG.md` with an inline `awk`/`sed`
snippet that scans from a version's `## [x.y.z]` heading up to the *next*
`## [` heading (or a stray top-level `# ` heading) for the GitHub Release
body. If you hand-edit `CHANGELOG.md`, keep that heading structure intact
or the extraction will grab the wrong range.
